## 1. [massive] Viewport-cull the full connection redraw pass: every full pass renders/measures ALL connections, visible or not

**Hot path:** User gesture -> drag end: `EmitEndDragSequenceEvent.handle` re-emits node changes (libs/f-flow/src/f-draggable/domain/emit-end-drag-sequence-event/emit-end-drag-sequence-event.ts:24-27) -> `FFlowComponent._runNodesPass` -> `EmitConnectionsChangesRequest()` with NO dirty node id (libs/f-flow/src/f-flow/f-flow.component.ts:285) -> connectionsChanges$ listener (f-flow.component.ts:302-318) -> `RedrawConnections.handle` resolves scope=null and takes `[...this._store.connections.getAll()]` (libs/f-flow/src/domain/f-connection/redraw-connections/redraw-connections.ts:27-49, line 36) -> worker batch build iterates every connection synchronously (worker/build-connection-worker-batch/build-connection-worker-batch.ts:21-37) or main-thread slices (pipeline/run-connection-redraw-slice/run-connection-redraw-slice.ts:36-72). The same full pass fires on initial render settle, on any connection add/remove (domain/f-connection/add-connection-to-store/add-connection-to-store.ts:15), after fit/center animations (domain/f-canvas/redraw-canvas-with-animation/redraw-canvas-with-animation.ts:48,57), and on `fConnection` input changes (f-connection/f-connection/f-connection.component.ts:125).

**Evidence:** Per connection per full pass, regardless of whether it is anywhere near the viewport: 2 connector-registry lookups (`findSourceConnector`/`findTargetConnector`, redraw-connections/shared/resolve-connection-endpoints/resolve-connection-endpoints.ts:17-19), 2 endpoint-rect resolutions where each per-pass-cache miss is a layout-forcing `getBoundingClientRect` because `fCache` defaults to disabled (f-cache/config/f-cache-options.ts:7-9 `enabled: false`; get-normalized-connector-rect.ts:36-57 -> \_libs/f-2d/rect/rect.extensions.ts:28-29), a ~20-field worker payload object per connection (worker/build-connection-worker-payload-item/build-connection-worker-payload-item.ts:19-50) or main-thread path construction, and a ~12-field render-signature string allocated even when the DOM write is then skipped (main-thread/apply-connection-render/apply-connection-render.ts:40-76). Asymptotics: O(C) with C = total connections; for C=5,000 that is ~10,000 gBCR-or-cache-key lookups + 5,000 signature/payload allocations per pass, and the apply phase runs in 6ms slices capped at 500 connections (run-connection-redraw-slice.ts:11-12), so even a mostly-no-op full pass occupies >=10 rAF frames (~60ms of main-thread work) after EVERY drag end. In the non-worker path the gBCR reads interleave with the previous connections' path writes inside one slice, so each cache-miss read is a forced synchronous layout. Pan/zoom itself is already cheap (one `style.transform` write, f-canvas/models/f-canvas-base.ts:163-166) - the waste is concentrated in these settle-point full passes. The docs guide (apps/f-flow-portal/public/markdown/guides/concepts/large-flow-performance.md) explicitly concedes there is no viewport culling.

**Proposal:** Add viewport culling inside `RedrawConnections.handle`, between scope resolution and the worker/slice split. (1) Compute the viewport rect in flow coordinates with pure model math - exactly the transform algebra `MinimapNodeRects.viewOffset` already uses (domain/minimap/minimap-node-rects.ts:36-50): `(transform.position + transform.scaledPosition)/scale` plus flow host client size cached via one ResizeObserver; inflate by ~50% margin. (2) Partition the connection list by whether the AABB union of the two endpoint NODE rects intersects it, using `connector.fNodeId` (already resolved at redraw-connections.ts:75-84) + `node._position` + the offsetWidth size-cache pattern MinimapNodeRects proves costs zero DOM reads (minimap-node-rects.ts:100-127); unknown size => treat as visible. (3) Render the visible partition through the existing worker/slice pipeline; stash the rest as a deferred set on `ConnectionRedrawState` tagged with the session. (4) Flush deferred connections incrementally from the existing `transformChanges$` channel with `debounceAnimationFrame` (the exact subscription pattern f-minimap.component.ts:77-84 uses), rendering only newly-visible ones per frame under the existing slice budget, and force-flush before `CalculateSelectableItems` (it gBCRs connection `boundingElement`s) and `getState(measuredSize)`. Ship it opt-in like fCache, e.g. `withViewportCulling()` / `[fCulling]`.

**Expected win:** Full-pass cost drops from O(total connections) to O(visible connections + delta per pan frame). A zoomed-in editor over a 5,000-connection graph typically shows 2-10% of them: the post-drag and initial-render passes shrink ~10-50x (60ms+ of sliced main-thread work plus thousands of allocations down to a few ms), and initial time-to-first-correct-paint improves the same way since only visible connections must be measured and pathed before the viewport looks right.

**Risk:** Fast pan can reveal connections whose path is stale or missing until the next flush frame (mitigated by the inflation margin and per-frame flush, but a worst-case one-frame pop-in is real). Any user code that reads an off-screen connection's SVG path DOM sees stale geometry until flushed. Selection-area and state-export paths must force-flush first or they compute wrong rects. Keeping it opt-in preserves default semantics but splits the test matrix.

**Verifier:** Every citation verified against the code. Hot path confirmed: raw mousemove (no rAF coalescing, drag-and-drop-base.ts:74) -> OnPointerMove.handle -> draggableItems.forEach (on-pointer-move.ts:36-38) -> SelectionAreaHandler.onPointerMove (selection-area-handler.ts:54-81), the sole handler during rubber-band (selection-area-preparation.ts:33). ## 2. [massive] fVirtualFor is progressive mounting, not virtualization: add viewport windowing (mount/unmount) so DOM and initial render scale with the viewport, not the graph

**Hot path:** Initial render: `FVirtualFor.ngOnChanges` -> `_renderProgressively` pumps `createEmbeddedView` for EVERY item under a 10ms/frame budget and never removes or skips any (libs/f-flow/src/f-virtual/f-virtual-for.ts:34-39, 55-124 - there is no transform subscription, no intersection test, no unmount path; the only removal is the wholesale `_vc.clear()` on input change, line 45-53). Every later user gesture then pays for the full DOM: pan/zoom composites and hit-tests n node subtrees, and every full connection pass (finding 1) walks connections of every mounted node.

**Evidence:** Per-event figures from the code: mounting is O(n) `createEmbeddedView` calls total - at the 10ms FRAME_BUDGET (f-virtual-for.ts:67) and a realistic 0.3-1ms per node view, 5,000 nodes take 1.5-5s of pumped frames before `fFullRendered` can fire, during which each chunk's connector registrations trigger `AddConnectionToStore.emitConnectionChanges()` full redraw passes over all connections mounted so far (add-connection-to-store.ts:15 -> f-flow.component.ts:302-318), i.e. a cumulative O(n^2/chunk) re-resolution of endpoints. Steady state: all n node components, their connectors' ResizeObservers, and all connection SVG elements stay in the DOM forever, so browser style/paint/hit-test and Angular memory are O(n) for the lifetime of the editor. The portal's own perf guide states the limitation verbatim: 'This is progressive creation, not viewport culling' (apps/f-flow-portal/public/markdown/guides/concepts/large-flow-performance.md). Nothing else in the library unmounts nodes: grep for culling/IntersectionObserver across libs/f-flow/src finds none.

**Proposal:** Extend `FVirtualFor` with an opt-in windowed mode: `*fVirtualFor="let n of nodes; trackBy: id; position: n.position; size: estimate"`. (1) Subscribe to `transformChanges$` piped through `debounceAnimationFrame` (the established pattern at f-minimap.component.ts:77-84). (2) Each frame, compute the visible index set by testing each item's position + cached-or-estimated size against the inflated flow-space viewport - the same pure-math viewport derivation as `MinimapNodeRects.viewOffset` (minimap-node-rects.ts:36-50); positions come from the data the template already binds to `fNodePosition`, so no DOM is needed. (3) Mount entering items with the existing calibrated budget pump; `ViewContainerRef.detach()` (not destroy) leaving views into a recycle pool so component state survives. (4) Keep connections to unmounted nodes drawable: persist their connector rects in `FCache` (its `connectorEntries` are already keyed by `FCacheConnectorKey`, not by live element - f-cache/model/f-cache.ts:11-13) by measuring on first mount and skipping unregister in windowed mode, so `ResolveConnectionEndpointRect` falls back to the id-keyed cache instead of a live element. Combined with finding 1, off-screen connections are deferred anyway, which removes most of the unresolved-endpoint pressure.

**Expected win:** Time until the viewport is fully populated becomes O(visible) instead of O(n): a 5,000-node graph showing ~150 nodes mounts ~30x less on startup (hundreds of ms instead of seconds to a complete-looking screen), steady-state DOM node count and Angular component count become bounded by viewport size + margin, and pan/zoom frame cost stops growing with graph size.

**Risk:** Highest of the three. Never-mounted nodes have no measured connector rects, so connections touching them need the model-size fallback (or stay deferred) until first mount - visible as endpoint pop-in. Detached-view recycling must be correct for stateful node components (forms, subscriptions), and fast panning can thrash mount/unmount without a generous margin and recycle pool. Public APIs that walk node host elements (fitToFlow, getState with measuredSize, a11y) need a documented force-mount or model-rect path. Must stay strictly opt-in.

**Verifier:** Every load-bearing citation verified against the code. f-virtual-for.ts is pure progressive mounting: ngOnChanges (34-39) pumps createEmbeddedView for all n items under FRAME_BUDGET=10 (line 67); the only removal is \_vc.clear() (45-53); no transform subscription, viewport test, or unmount path exists, and a repo-wide grep finds no culling/IntersectionObserver anywhere in libs/f-flow/src. The portal guide admits the limitation verbatim (large-flow-performance.md:57). ## 3. [large] Selection-area drag performs O(n) classList writes and ~2n rect allocations on every pointermove

**Hot path:** User gesture: pointer-drag to rubber-band select -> `SelectionAreaHandler.onPointerMove` (libs/f-flow/src/f-draggable/selection-area/selection-area-handler/selection-area-handler.ts:54-81): the `_canBeSelected.forEach` at lines 66-80 runs for every selectable node AND connection on every pointermove; drag start runs `prepareDragSequence` -> `CalculateSelectableItems.handle` (domain/f-selection/calculate-selectable-items/calculate-selectable-items.ts:28-32), which executes `GetNormalizedElementRectRequest` -> `RectExtensions.fromElement` -> `getBoundingClientRect` for every node and every connection (get-normalized-element-rect.ts:34-44, rect.extensions.ts:28-29, cache-gated by the default-off fCache).

**Evidence:** Per pointermove, for EVERY item whether or not it is near the selection box: `item.element.unmarkAsSelected()` -> unconditional `hostElement.classList.remove('f-selected')` (mixins/change-selection/change-selection.ts:20-23), two fresh rect objects from `RectExtensions.mult` + `RectExtensions.addPoint` (selection-area-handler.ts:69-72; rect.extensions.ts:68-82 both allocate), one intersection test, and for intersecting items `markAsSelected()` -> `classList.contains` + `classList.add` (change-selection.ts:25-34). With 5,000 nodes + 5,000 connections that is ~10,000 classList calls + ~20,000 allocations per move at 60-125Hz pointermove rate (~1-2M DOM calls/s), plus a re-selected item is removed-then-re-added each move, invalidating its style every frame. Drag start additionally forces n+m `getBoundingClientRect` reads and an O(n\*s) `selectedItems.includes` filter (calculate-selectable-items.ts:29-31). Nothing here is viewport- or delta-aware.

**Proposal:** Make the per-move work proportional to the selection delta. (1) At `prepareDragSequence`, pre-transform all item rects into screen space ONCE (`mult(scale)` + `addPoint(canvasPosition)`) and store them flat (Float64Array or plain array of frozen rects); recompute only when the transform actually changes mid-drag (auto-pan) - the handler already knows, it calls `NotifyTransformChangedRequest` itself (selection-area-handler.ts:81). (2) Per pointermove, intersect against the cached screen rects with zero allocations, building a `newSelected: Set<ISelectable>`; diff against the previous set and call `markAsSelected`/`unmarkAsSelected` only on the symmetric difference - typically 0-5 items per move instead of n. (3) Optionally sort rects by x (or bucket into a coarse grid) at drag start so each move tests only candidates overlapping the box's x-range, making the scan sublinear too. (4) Replace the `includes` filter with a Set. This builds on nothing new - it is the same reuse-and-diff discipline `MinimapDrawNodes` already applies to its rects and class strings (minimap-draw-nodes/minimap-draw-nodes.ts:62-76).

**Expected win:** Per-pointermove cost during rubber-band selection drops from ~3n DOM calls + 2n allocations to an O(delta) handful; on 5k-10k element graphs the gesture goes from visibly janky (multi-ms scripting + style invalidation per move) to sub-millisecond, restoring 60fps for a core editor interaction. Drag-start cost also stops double-paying once rects are read once and reused.

**Risk:** Low. Semantics are preserved by construction (same intersection predicate, classes toggled only on change). The two edge cases to cover are auto-pan mid-drag (cached screen rects must be rebuilt on transform change - the hook already exists in the handler) and external selection mutations during a drag, which today are clobbered by the unconditional unmark anyway.
